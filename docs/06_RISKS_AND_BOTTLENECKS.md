# 06 — Risks, Bottlenecks and Edge Cases

Status: **proposed, awaiting approval**. Every mitigation here follows `docs/00_DECISIONS.md`.

**How to read the tables**

- **L/S** is likelihood / severity (H = high, M = medium, L = low).
- **Phase** refers to the phases in `PROJECT_TODO.md`:

| Phase | Covers |
|---|---|
| P3 | Schema and seed |
| P4 | APIs |
| P5 | Auth |
| P6 | Customer UI |
| P7 | Feedback and ratings |
| P8 | AI |
| P9 | Recommendations |
| P10 | Analytics |
| P11 | DBMS objects |
| P12 | Testing |
| P13 | Documentation |

- **Verified by** names the test or check that proves the mitigation works. `constraint_tests.sql` is `database/tests/constraint_tests.sql`, and API tests live in `backend/tests/` (node:test with supertest).

Severity reflects this project: a live university demonstration on one laptop with about 25 users and about 200 reviews. Problems that only appear at web scale are not listed.

## 2. Database

| ID | Risk | Cause | Impact | L/S | Mitigation | Phase | Verified by |
|---|---|---|---|---|---|---|---|
| DB-01 | Duplicate ratings | A double-clicked submit, two tabs, or a client bug. | The average rating is inflated. | H/H | • `UNIQUE(user_id, product_id)` on `ratings` and `UNIQUE(rating_id)` on `feedback`.<br>• `sp_submit_review` upserts with `INSERT … ON DUPLICATE KEY UPDATE`, so a second submit edits rather than inserts.<br>• The submit button is disabled while the request is in flight. | P3, P7, P11 | `constraint_tests.sql` asserts a duplicate insert fails with 1062. An API test sends two parallel POSTs and expects 1 rating row. |
| DB-02 | Invalid foreign keys | The client sends a non-existent product or user ID. | 500 errors, or orphan rows if FKs were missing. | M/M | • Every relationship is a declared FK in InnoDB.<br>• The API validates IDs with zod and maps ER_NO_REFERENCED_ROW_2 (1452) to 404/422 instead of 500. | P3, P4 | `constraint_tests.sql` (insert with a bad FK must fail). API tests check the error codes. |
| DB-03 | Orphaned feedback | Feedback that outlives its rating or user. | Reviews with no author or product in analytics. | L/H | • `feedback.rating_id` is NOT NULL with a CASCADE FK. User and product are reached only through `ratings`, so there is nothing else to orphan.<br>• `sentiment_analysis` and `aspect_sentiments` cascade from feedback. | P3 | An orphan-check query in `constraint_tests.sql` (LEFT JOIN … IS NULL) returns 0. |
| DB-04 | Inconsistent sentiment records | Several analyses per review. A COMPLETED status with no label. A stale analysis after the text is edited. | Dashboard counts that do not add up. | M/H | • `UNIQUE(feedback_id)` on `sentiment_analysis`.<br>• CHECK: COMPLETED requires a label, scores and `analyzed_at`.<br>• `trg_feedback_after_update` resets to PENDING and deletes the aspect rows when the body changes.<br>• `text_sha256` detects stale results: the worker discards a result whose hash no longer matches the current body. | P3, P8, P11 | Constraint tests. A test edits a review and expects PENDING. The P12 consistency query shows the sentiment counts summing to the COMPLETED count. |
| DB-05 | Slow aggregate queries | Views like `v_product_performance` and `v_category_sentiment` join 5–6 tables and are evaluated on every dashboard load. | The dashboard is sluggish. Negligible at 200 reviews, but it shows poor design. | L/L | • The indexes listed in 00_DECISIONS: `ratings(product_id, stars)`, `feedback(status, created_at)`, `sentiment_analysis(label)`, and others.<br>• Filters are pushed into the WHERE clause before GROUP BY.<br>• One query per chart, not N+1.<br>• No materialised tables: derived values stay derived. | P10 | `EXPLAIN` for each analytics query is captured in `04_DBMS_OBJECTS_AND_QUERIES.md` (no full scans on large tables). Response times are logged. |
| DB-06 | Missing indexes | FK columns and filter columns left unindexed. | Full scans and lock contention on FK checks. | L/M | • InnoDB auto-indexes FKs.<br>• Composite indexes for each real access path (in 00_DECISIONS).<br>• FULLTEXT on products for search. | P3 | `SHOW INDEX` is reviewed against the list of query access paths. |
| DB-07 | Incorrect cascade deletion | The InventoryOS pattern `orders.customer_id ON DELETE CASCADE` silently erased history. | Deleting a category or product wipes out its reviews. | M/H | • Explicit policy: categories → products is RESTRICT. Products → ratings and interactions is RESTRICT, so products are **archived** with `is_active=0`.<br>• User delete cascades to that user's own data only, needs typed confirmation, and suspension is the default.<br>• `trg_users_before_delete` blocks deleting the last admin.<br>• Triggers do **not** fire on cascaded rows, so cascades are never relied on for audit. The app writes `audit_log` before the delete. | P3, P4, P11 | Constraint tests: deleting a category with products fails (1451), and deleting a product with ratings fails. An admin API test expects a 409 with an "archive instead" message. |
| DB-08 | Race conditions | Two concurrent review submissions, or two analysis workers claiming the same row. | Duplicate rows, or the same review analysed twice. | M/M | • Reviews: the unique keys plus upsert inside one transaction (`sp_submit_review`).<br>• Worker: claims with `UPDATE … SET status='PROCESSING' WHERE analysis_id=? AND status IN ('PENDING','FAILED')`. Only the request with `affectedRows=1` proceeds.<br>• A row left in PROCESSING for more than 5 minutes (a crash) is re-claimable. | P7, P8 | A parallel-submit API test. A worker unit test that runs two claims and expects one winner. |
| DB-09 | Duplicate seed records | Re-running the seeder. | Doubled users, reviews and statistics. | H/H | • Upsert on natural keys: `users.email`, `products.slug`, `(user_id, product_id)`, `(rating_id)`, and the batch label.<br>• Interactions are keyed `(user_id, interaction_type, product_id/category_id/search_query, occurred_at)`. The seeder deletes and re-inserts only rows of its own `seed_batch_id`, inside the same transaction.<br>• Never TRUNCATE. | P3 | Run the seeder twice and compare per-table row counts. They must be identical. |
| DB-10 | Incorrect average rating | Averaging feedback instead of ratings, counting HIDDEN rows inconsistently, integer division, or one 5★ review topping the chart. | Wrong rankings and "best product" claims. | M/H | • `v_product_rating_stats` uses `AVG(stars)` over `ratings` only, `ROUND(…, 2)` on DECIMAL output, and `COUNT(*)` from the same rows.<br>• A Bayesian average (C=5 against the global mean) is used for rankings.<br>• `HAVING COUNT(*) >= min_reviews` on "top" lists.<br>• One documented rule: HIDDEN feedback text is excluded from text analytics, but its rating still counts. | P10, P11 | A test fixture of 3 products with known ratings checks hand-computed averages. The dashboard total equals `SELECT COUNT(*) FROM ratings`. |

## 3. Backend

| ID | Risk | Cause | Impact | L/S | Mitigation | Phase | Verified by |
|---|---|---|---|---|---|---|---|
| BE-01 | SQL injection | String-built SQL. InventoryOS interpolates `${where}` clauses, which are safe today but a fragile pattern. | Data theft or destruction. | L/H | • All values go through `?` placeholders.<br>• Dynamic ORDER BY and filter columns come only from a server-side allow-list map (`sort=avg_rating` → `ps.avg_rating`), never from raw input.<br>• `multipleStatements` stays off. | P4 | API tests send `' OR 1=1 --` and `; DROP` payloads to search and sort parameters. A grep check finds no template literal containing `req.` inside SQL. |
| BE-02 | Missing validation | Ad-hoc checks (InventoryOS `updateProduct` accepts anything). | Bad data, 500s, and DB-level errors leaking out. | H/M | • A zod schema per route (body, params, query) through `validate()` middleware. It returns 422 with `error.fields`.<br>• The DB CHECK constraints act as a second line of defence. | P4 | Each route has a test for invalid input that expects 422. |
| BE-03 | Unhandled exceptions | Express 4 does not catch rejected async handlers. `await db.getConnection()` sits outside try/catch. | A crashed or hung request, or a dead process. | H/H | • `asyncHandler` wrapper (or `express-async-errors`-style pattern written in-house) on every route.<br>• Connections are acquired inside try with release in `finally`.<br>• `process.on('unhandledRejection')` logs and exits non-zero in dev. | P4 | A test stops the DB, hits an endpoint and expects a 503 JSON envelope with the process still alive. |
| BE-04 | Inconsistent API responses | Each controller shapes JSON differently. | Frontend bugs and duplicated parsing. | M/M | A single envelope (`{success, data, meta}` / `{success:false, error:{code,message,fields}}`) produced by `utils/apiResponse.js` and the central error handler. | P4 | Contract tests assert the envelope shape on every route. |
| BE-05 | Missing authorization | InventoryOS has none, and P4 (APIs) comes before P5 (auth) in the plan. | Customers reach admin routes, and users read each other's data (IDOR via `customer_id`). | H/H | • `requireAuth` and `requireRole('ADMIN')` middleware are written at the **start of P4**, so no route ships unauthenticated.<br>• The user ID always comes from the JWT, never from the body or params.<br>• `requireAuth` re-reads `users.status` by primary key, so a **suspended user's 8-hour token stops working immediately**. | P4, P5 | A route matrix test: every admin route returns 401 anonymous, 403 for a customer and 200 for an admin. A test shows customer A cannot read B's feedback. |
| BE-06 | Exposed credentials | `.env` copies (`Archive.zip`, `.env.backup`), error messages returning `error.message`, logging of request bodies. | Leaked DB, JWT or internal-token secrets, or password hashes. | M/H | • `.env` is gitignored and `.env.example` has placeholders only.<br>• The error handler never returns internal messages.<br>• Logs record method, path, status and time only, never bodies.<br>• `password_hash` is never selected into API responses (explicit column lists, no `SELECT *` on users).<br>• `helmet` is enabled.<br>• Startup aborts if `JWT_SECRET` is shorter than 32 characters. | P4, P5 | `git ls-files` shows no `.env`. A test confirms `/api/admin/users` responses contain no `password_hash`. Triggering an error returns no stack. |
| BE-07 | Duplicate API requests | Double clicks and retried network calls. | Duplicate rows, double analysis. | M/M | • Unique keys plus upsert (DB-01).<br>• The worker's hash check means repeated analysis of the same text is skipped.<br>• The frontend disables buttons during requests. | P7 | The parallel-POST test from DB-01. |
| BE-08 | Incorrect pagination | OFFSET without a stable ORDER BY, or a total counted over different filters than the rows. | Rows skipped or repeated, and wrong page counts. | M/M | • `utils/pagination.js`: `page >= 1`, `pageSize` 1–100 (default 20).<br>• `ORDER BY <allow-listed column>, <pk>` as a tiebreaker.<br>• The count query reuses the same WHERE builder and parameters.<br>• Numbers are cast to ints and passed as placeholders. | P4 | A test pages through all feedback and checks the union of IDs equals the full set with no duplicates, and that `meta.total` matches. |
| BE-09 | Large response payloads | Returning every row (as InventoryOS does) or full review bodies in lists. | Slow pages and memory spikes. | M/L | • Pagination everywhere.<br>• List endpoints return a body excerpt (`LEFT(body, 280)`), and the full text only on the detail view.<br>• CSV export streams rows. | P4, P10 | The response size of list endpoints is checked in tests (under 100 KB at pageSize=20). |
| BE-10 | SIGNAL errors surface as 500 | Triggers and `sp_submit_review` raise SQLSTATE 45000 for business rules (inactive product, suspended user, last admin). | The user sees "Internal Server Error" for a legitimate rule. | M/M | The error handler maps SQLSTATE 45000 to 409/422 with the trigger's MESSAGE_TEXT (authored by us, safe to show), 1062 to 409, and 1451/1452 to 409/422. | P4, P11 | Tests for rating an archived product (409) and deleting the last admin (409). |

## 4. AI service

| ID | Risk | Cause | Impact | L/S | Mitigation | Phase | Verified by |
|---|---|---|---|---|---|---|---|
| AI-01 | Slow model initialisation | RoBERTa-base load and tokenizer warm-up takes about 5–20 seconds on CPU. | Requests during startup fail. A slow demo start. | H/L | • Load in the FastAPI lifespan, followed by one warm-up inference.<br>• `/health` returns 503 until ready.<br>• Express treats 503 as "pending", and the worker retries later. | P8 | A startup log records the load time. A test confirms `/health` is 503 before load and 200 after. |
| AI-02 | Repeated model loading | Loading inside the request handler, or multiple uvicorn workers. | Seconds per request, and RAM multiplied by the worker count. | M/H | • A single module-level pipeline created once in the lifespan.<br>• uvicorn with `--workers 1`.<br>• Inference runs in a threadpool so the event loop stays responsive. | P8 | A test calls `/v1/analyze` 10 times and asserts the load counter is still 1. |
| AI-03 | High memory consumption | Torch with RoBERTa uses about 1–1.5 GB resident, and batch size multiplies activations. | Laptop swapping during the demo. | M/M | • CPU only.<br>• `torch.set_num_threads` capped.<br>• Batch size at most 32 (the API limit), and seed analysis in chunks of 16.<br>• `torch.inference_mode()`.<br>• No second model in memory. | P8 | RSS is logged at `/health` (`psutil` is optional; skip it if not installed). |
| AI-04 | AI service downtime | The service is not started, has crashed, or is still loading. | Without handling, review submission would fail. | H/H | • Reviews are committed first (201 response) and analysis runs asynchronously.<br>• The 8-second timeout marks the row FAILED and increments `attempt_count`.<br>• The worker retries every 60 seconds, up to 5 attempts.<br>• The UI shows "Analysis pending".<br>• Admins can re-queue FAILED rows.<br>• Analytics show "n reviews awaiting analysis" instead of silently excluding them. | P7, P8 | Integration test: stop the AI service, submit a review, and get a 201 with a PENDING row. Start the service and the row reaches COMPLETED within 2 minutes. |
| AI-05 | Invalid sentiment responses | A malformed JSON, missing scores, scores that do not sum to about 1, or an unknown label. | Corrupt rows or crashes. | L/M | • Express validates the response with a zod schema: label in the enum, each score 0–1, and the sum within ±0.01. Anything else counts as FAILED with `last_error`.<br>• The DB CHECKs (score range, COMPLETED needs a label) are the last line of defence. | P8 | Unit test with a mocked AI response for each malformed case. |
| AI-06 | Confidence misinterpretation | A softmax probability is not a calibrated confidence, and a 3-class minimum is about 0.33. | Admins over-trust a 0.41 "positive". | M/M | • Confidence is derived as the score of the stored label (in a view, not stored).<br>• The UI shows bands (Low < 0.55, Medium < 0.80, High) with an explanation tooltip.<br>• Below 0.55 the policy assigns NEUTRAL.<br>• Analytics can filter to High confidence. | P8, P10 | The evaluation report includes a reliability table (accuracy per confidence band). |
| AI-07 | Mixed feedback misread | A 3-class model gives one label to "great sound, terrible battery". | Complaints hidden inside positive labels. | H/M | • A separate aspect module splits clauses at contrast markers and classifies each matched clause.<br>• `is_mixed` is derived when both POSITIVE and NEGATIVE aspects exist.<br>• If the same aspect appears in several clauses, store the clause with the strongest score (because of the `UNIQUE(analysis_id, aspect_id)` key) and note that in the evidence.<br>• Documented honestly as lexicon plus clause-level sentiment, **not** trained ABSA. | P8 | Golden tests for 15 or more hand-labelled mixed sentences, e.g. the brief's headphones example yields sound = POSITIVE, battery = NEGATIVE and is_mixed. |
| AI-08 | Model performance limits | Sarcasm, negation ("not bad"), domain slang, very short reviews ("ok."). | Some wrong labels. | H/L | • Document the limits.<br>• Report measured accuracy in place of claims.<br>• Reviews under 3 words get a neutral-leaning threshold.<br>• Admins can see the scores per review. | P8, P13 | The evaluation report lists error categories with examples. |
| AI-09 | Unsupported language | Hindi or Telugu text typed by a demo user. langdetect is non-deterministic and unreliable on short text. | Garbage labels on non-English text. | M/L | • `DetectorFactory.seed = 0` for determinism.<br>• Only detect when the text has at least 20 characters. Shorter text is assumed English.<br>• Non-`en` text gets the `UNSUPPORTED` status with no label, and is shown as "Not analysed (language)". | P8 | Unit tests with Hindi, French and short English samples. |
| AI-10 | Long and empty input | Pasted essays, whitespace-only text. | Truncation that hides the tail of a review, or a model error. | M/L | • Express rejects bodies under 10 or over 4000 characters (matching the DB CHECK).<br>• The AI service rejects empty text with 422 and text over 4000 characters with 413.<br>• Overall sentiment truncates at 512 tokens with `was_truncated=1`, but aspect analysis covers **all** clauses, so the tail still contributes. | P7, P8 | Boundary tests at 9, 10, 4000 and 4001 characters. A 3000-character review yields `was_truncated=1` and aspects from the final paragraph. |
| AI-11 | Unauthenticated access to the AI service | Any local process can POST to 8001. | Low on a laptop, but it bypasses Express. | L/L | Bound to 127.0.0.1 only, and `X-Internal-Token` is required (secret in both `.env` files). | P8 | A request without the token returns 401. |

## 6. Recommendations

| ID | Risk | Cause | Impact | L/S | Mitigation | Phase | Verified by |
|---|---|---|---|---|---|---|---|
| RE-01 | New-user cold start | No ratings or views. | An empty or random list. | H/M | • `COLD_START` strategy: preferred categories chosen at registration (optional, multi-select), plus top Bayesian-rated products.<br>• With no preferences: popular (reviews in the last 90 days) plus top rated, requiring at least 3 reviews.<br>• `strategy` is stored on the run. | P9 | A freshly registered user gets 10 recommendations, each with a fallback `reason_code`. |
| RE-02 | Repeated recommendations | A deterministic score returns the same top 10 every visit. | Users stop trusting the page. | H/M | • Exclude products shown in the last 3 runs without a click.<br>• Exclude products dismissed in the last 30 days and products already rated.<br>• Regenerate only when stale (24 hours or new activity). | P9 | A test generates 3 runs with no clicks and checks the overlap between run 1 and run 4 is below 100%. |
| RE-03 | Biased recommendations | The quality prior and popularity favour already-popular products, and the seed data is skewed. | A rich-get-richer list with the same bestsellers everywhere. | M/M | • Bayesian shrinkage (C=5) instead of the raw average.<br>• The popularity weight is used only in the fallback.<br>• Diversity cap of 3 per category in the top 10.<br>• Weights are fixed and documented, not hidden. | P9 | An analysis query shows the distribution of recommended products across all seed users (no single product in more than 60% of lists). |
| RE-04 | Irrelevant category matching | Category-only matching recommends a book to someone who rated one book 1★. | Off-target suggestions. | M/M | • Rating weights are centred at (stars − 3), so a 1–2★ rating **reduces** affinity for that product's tags and category.<br>• Tag cosine similarity carries the most weight (0.40) over category (0.25). | P9 | Fixture user who rated Books 1★ and Electronics 5★: no book appears in the top 5. |
| RE-05 | Thin interaction history | A user with a single view. | Overfitting to one product. | M/L | • Blend: when the profile weight is below a threshold, mix COLD_START candidates in, ranked by the same score.<br>• Recency decay (14-day half-life) prevents one old view from dominating. | P9 | Fixture user with a single view gets mixed reason codes. |
| RE-06 | No explanation | A score with no reasoning. | Not explainable, which weakens the "AI" claim. | L/H | Every row stores `reason_code` and `reason_text`, taken from the strongest scoring term, with an anchor product ("Because you rated X 5★", "Popular in Fitness this quarter"). The UI shows it on every card. | P9 | A DB CHECK via NOT NULL. A test confirms no recommendation has an empty `reason_text`. |
| RE-07 | Search terms not matching | InnoDB FULLTEXT ignores tokens shorter than `innodb_ft_min_token_size` (3) and stopwords, so "tv" and "4k" fail. | Search-based signals and the Explore search miss obvious products. | M/L | • Use `MATCH … AGAINST` in boolean mode for terms of 3 or more characters.<br>• Fall back to `LIKE` on name and brand for shorter terms.<br>• Both paths use placeholders. | P4, P9 | Search tests for "tv", "headphones" and "noise cancel". |

## 7. Deliberately not doing

These are skipped on purpose. Each would add moving parts to a single-laptop demo without fixing a real problem at this scale.

| Not doing | Why |
|---|---|
| **Redis or another cache** | About 200 reviews and indexed MySQL queries return in milliseconds. A cache would add an invalidation problem (stale dashboards, see FE-05) to solve a speed problem we do not have. |
| **Message queue (RabbitMQ, Kafka, BullMQ)** | The `sentiment_analysis.status` column *is* the queue. The in-process worker with a guarded claim (DB-08) is durable because state lives in MySQL, and it demonstrates transactions and locking. |
| **Docker requirement** | MySQL 8.0.46, Node and (after setup) Python are already native on the machine. Docker would add a second MySQL and more port conflicts (ENV-05). A Compose file can be an optional extra in P13. |
| **Collaborative filtering** | With 23 customers the user–item matrix is too sparse for meaningful similarity, and the brief forbids claiming it unless it is real. The engine is content-based and explainable (`cb-1.0`), and the docs say so. |
| **Trained aspect-based sentiment (ABSA) model** | A second large model doubles memory (AI-03) and download size (ENV-06). Lexicon plus clause-level sentiment is honest, explainable and testable. A trained ABSA model is listed as future work. |
| **Materialised summary tables** | Storing averages and counts duplicates derivable data (the brief's 3NF rule) and creates consistency risk (DB-10). Views compute them on demand. |
| **Refresh-token rotation, OAuth, email verification** | Out of scope for the demo. One httpOnly JWT cookie with a per-request status check (BE-05) covers role enforcement and suspension. |
| **Cloud or paid APIs** | The brief requires local inference. The model is cached locally (ENV-06). |
| **Frontend state library (Redux, React Query)** | A small `useApi` hook with `reload()` covers loading, error and refresh needs (FE-04, FE-05) across about 20 pages. |
